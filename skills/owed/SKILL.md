---
name: owed
description: An acceptance ledger for multi-agent task graphs. Use owed to dispatch worktrees, collect measured and independent review evidence, explain rejections and debt, and check acceptance conditions before merging.

# owed: No receipt, not done.

**You, the main agent, are the owner (D25).** A human states the task and leaves; no human operates owed. Owner tools (`owed_waive`, `owed_defer`, `owed_adopt`, `owed_approve`, owner `owed_evidence`, `owed_init`, `owed_decoy` commit/reveal, downgrading `owed_plan`) run without a dialog as `owner:pi` and are recorded with channel `delegated`; the brief lists them first, so the morning reader audits them. Never ask a human to run an owed command, and never use `--i-am-owner`. Every act that eases acceptance (a plan downgrade: `note`; waive/defer: `reason`; adopt: `note`) must say why — owed refuses it otherwise. Subagents (writers, reviewers, any pi-durable-subagents call) never act as owner or parent: owed refuses those acts in a process with `DSA_CALL`/`DSA_EXEC` (an accident rail, not a security boundary); such a process also cannot record a review or evidence on a node from inside that node's slot worktree (review from the repository root). Never claim `parent:drive` (the driver's identity; refused). When you judge a candidate (review, waive, approve, owner review, evidence), pass the commit you actually read: `candidate` (CLI `--candidate <commit12>`, as every command owed suggests already carries); if the writer submitted again meanwhile, owed refuses with `candidate changed` and records nothing: re-read `owed_why` and judge the new candidate. Only when the environment sets `OWED_CONFIRM=owner` do owner tools ask the human in a dialog (it times out after `OWED_CONFIRM_TIMEOUT` seconds, default 120, recording nothing); then continue other work and report the pending decision.

Every `owed_*` tool takes an optional `cwd`: the absolute path of a directory inside the target repository (default: the session's working directory). A session started elsewhere passes `cwd` on every call to drive another repository; relative paths such as `owed_plan`'s `plan` and `owed_decoy`'s `file` resolve against it. To submit as the slot writer, pass the slot worktree as `cwd`.

Start with `owed_brief` (CLI `owed brief [--since seq|ISO]`): owner decisions with the exact command that discharges each, merges since `since`, rejected or blocked nodes and how to clear them, work in progress with its age, and totals.

1. Use `owed_status` (CLI `owed status`) to inspect ready nodes and pending queues. Dependencies must have merge records before dispatch; a verbal claim of completion is not a receipt.
2. Use `owed_dispatch` to dispatch a ready node. Pass its `subagents` object to subagents/dsa: `agent: worker`, `cwd` must be the slot worktree, `isolation: none`, and `task` must contain the complete packet. owed has already created an isolated worktree; do not add another isolation layer.
3. Writers modify only the packet's writes scope, commit their work, and keep the worktree clean. Run `owed submit <node>` or `owed_submit` inside that worktree. A parent submitting on behalf of a writer must explicitly use the slot's `writer:<node>#<attempt>` identity.
4. Use `owed_attest` (CLI `owed attest <node>`) for executor measurements. Rerun attribution for original failures first, then process the current candidate. Read logs and rejection reasons; after repairs, commit, submit, and attest.
5. Start a fresh, independent reviewer with the current diff, packet, receipt card, and failure evidence. The reviewer must not have been a writer for any attempt of the node. Use `owed_review` with an independent `reviewer:id`, rank, verdict, and note. Closure changes require `closure-review` at rank 2 or higher. Read new rulings and acknowledge their seq with `ack_rulings`. If the brief or plan is ambiguous or contradictory, or the fix needs a product or contract decision, the reviewer blocks with `needs_parent: true` (CLI `--block --needs-parent`) and states the decision needed; it does not push a guess onto the writer. The parent answers with `owed_rule` / `owed rule --nodes <node> "<decision>"` (a `*` ruling does not resolve it); `owed drive` halts on such a block until that ruling exists, then sends the writer a repair that quotes it.
6. The parent inspects receipts and actual changes, then uses `owed_merge`. It checks the merge tree, invariants, and trunk CAS; neither review ok nor an accepted candidate replaces the merge guard. After merging, use `owed_report` to report evidence, waivers, and remaining debt.

7. If an attempt is a dead end, the parent closes its slot with `owed_abandon` (`node`, optional `reason`); the node can then be dispatched again. Periodically run `owed_gc` (first with `dry_run: true`) to remove worktrees and branches of merged or abandoned attempts; it never removes an open slot, a dirty or locked worktree, and it pins submitted commits under `refs/owed/keep/`. Use `owed_verify` to check the ledger hash chain.
8. If `owed_status` reports "trunk moved outside owed" (or a merge refuses the trunk CAS naming `owed adopt`), commits were made on trunk directly. Do not move refs to work around it. You, the main agent, are the owner: review those commits (`git log`/`git diff` of the range) and, if they belong on trunk, adopt them yourself with `owed_adopt` (`note` saying what they are and why they are acceptable, optional `commit`; delegated, no dialog) or `owed adopt --note TEXT`; list the adoption in your report. If they do not belong, revert or move them on trunk first. When the plan has an `allow` rule with `adopt` prefixes and every changed path lies under them, the parent may adopt itself: `owed_adopt` with `as: parent:<id>` (no dialog) or `owed adopt --note TEXT --as parent:<id>`. A diverged/rewritten trunk cannot be adopted: restore it (reset the trunk ref to the ledger trunk commit after saving the extra commits on a branch), then redo the work through owed.
8a. Worktree layout (plan `worktrees: {root, branch}`, node `type`): slots may live outside the repository and branches follow a template such as `"{type}/{node}-{attempt}"`. Always use the `worktree` and `branch` that `owed_dispatch` returns (the `owed_dispatch` result details and the CLI `owed dispatch` text carry both, the packet's `Working directory` is the worktree, and `owed status --json` has them under `nodes.<id>.slot`; the status and why texts do not show them); never derive them from `.owed/wt` or `owed/<node>/<attempt>`. Changing `worktrees` or `type` is not a downgrade and affects only later dispatches. If `owed_status` says `Trunk <name> is checked out at <path>; merges fast-forward it there (keep it clean).`, do not write in that worktree; when a merge refuses with `trunk worktree <path> has uncommitted changes`, inspect them: commit them there if they are wanted work, otherwise run `git -C <path> switch --detach` (never discard them), then retry the merge and say what you did in your report.
9. A defect found after a merge is recorded with `owed_escape` (`node`, `merge` = seq of that merge entry, `class`, `note`, optional `evidence`). Decoys belong to the owner: `owed_decoy` with `action: digest` only computes a digest; `commit` and `reveal` are owner acts the main agent makes itself (delegated, no dialog; a UI confirmation only under `OWED_CONFIRM=owner`) — a subagent never does.

10. `owed drive` (CLI; pi tool `owed_drive` = one pass, `--once`) runs dispatch → writer → submit → attest → reviewers → merge through pi-durable-subagents (≥ 1.0.27) as `parent:drive`. Run the long loop in a terminal or a `systemd-run --user` unit, never inside a tool or dsa call. A ruling recorded while a driver writer or reviewer call is running is steered to it (send reason `ruling`); it does not acknowledge anything, so reviewers still pass `ack_rulings`. Answer an asking call with the address the driver prints (pi `subagents` send `to: "<wid>/<key>"`, `qid`; or the CLI form). The driver never answers a run's question, never waives, never changes the plan, never runs `restart --force`, and never touches a node that needs the owner; it prints those. Attest goes through `hold machine --shared --no-wait`: a busy machine is retried next pass; an older dsa that rejects `--no-wait` halts the attempt with that error (upgrade dsa). A driver halt (status "Halted (driver)" / Pending owner, `owed why`) is cleared by any later action on that node by someone other than `parent:drive` — fix the cause, then e.g. submit, review, rebase, abandon (a new attempt), or record a ruling naming the node — and the driver resumes on its next pass (it keeps no verdict in memory). Exception: a halt from dsa rejecting a run or send is recognised by the abandon recovery sentence at its end (it may start with `dsa rejected`, `writer run … sealed rejected` or `review-missing: … sealed rejected`). The request is fixed for that attempt — its id and bytes cannot change and dsa answers the same way, so a ruling/submit/review only clears it until the retry re-halts; fix the cause (plan, agent, model), then `owed abandon <node>` so the driver starts a new attempt. If `owed drive` refuses because `.git/owed/drive.lock` is held by another host, check that host; only if no driver runs there, remove the lock file by hand (never for a lock of this host: a live driver holds it).

11. To run a DAG to completion from pi, call `owed_drive` with `action: "start"` once (CLI `owed drive --detach`): it starts the loop driver as a detached background process (log `.git/owed/drive/log.jsonl`) that survives pi. Then stop working on it and wait to be woken: the session gets one `owed-drive` follow-up message when the driver halts, a node needs the owner, a run asks a question, the driver is stalled, dsa events fail, or the driver exits (merges are listed in the next message); every top-level pi session later opened in the repository follows a running driver and is woken too, while sessions inside a dsa call (subagent writers/reviewers) do not attach by themselves. A halt or notify wakes again only when its text changed or the node gained ledger entries not written by the driver; a repeat without new entries rides along with the next message as `(repeat n, no new ledger entries)`. A halt that needs the owner reads `needs the owner (the main agent decides; owed lists the command)` and ends with the commands that resolve it. Trunk drift is not a halt: the driver merges nothing and notifies `trunk <name> moved outside owed (…); the main agent resolves it with: owed adopt --note "<why>"` (or, for a rewound trunk, the `git update-ref` that restores it); after the adopt the next pass merges. A drift halt left by a 0.5.0 driver is cleared with `owed rebase <node>`; you are the owner: run them (CLI owner acts are recorded as `owner:cli`, pi tools as `owner:pi`). Never poll `action: "status"` (or `owed drive --status`) in a loop; read it only when a message or the user asks. On a wake-up, read `owed_status` / `owed_why <node>`, act on the halt or question as in item 10 (the running driver resumes by itself on its next pass), and do not start a second driver (start refuses while one runs). When the plan will grow (you will add nodes as work proceeds), start it with `stay: true` (`owed drive --detach --stay`): when idle it wakes you once (`idle: …; staying until the ledger changes`) and resumes by itself after your next `owed_plan`, instead of exiting; stop it with `action: "stop"` when the work is done. After `owed_plan`, a line `ready: <ids> (<n>); no driver is running: …` means ready nodes wait and no driver runs: start one if you want them driven. Wakes are held while you are working and delivered when your turn ends, minus what you resolved meanwhile (`(<n> wake(s) resolved before delivery)`). `action: "stop"` (`owed drive --stop`) stops it after its current action, `now: true` at once; a stopped or SIGKILLed driver is restarted with `action: "start"`. Prefer starting it from a top-level session (or `systemd-run --user owed drive`): the driver drops `DSA_EXEC`/`DSA_CALL`, but started from inside a dsa call it prints `note: started from inside a dsa call; …` because that call's process containment may still end it with the call.

    Sessions (pi-durable-subagents ≥ 1.0.31): the driver's runs are listed in the pi session that started it (`DSA_SESSION`, recorded in `drive.lock`, passed as `run --session`); `owed_drive` status and `/owed` say `runs are listed in pi session <id>` or `no pi session: runs show only in pi-durable-subagents status / the CLI`. If another session should see them, stop the driver and start it from that session. An older dsa without `--session` is used without it (one log line, no halt).

12. Nodes with `approve: owner` (e.g. a publish or push) owe an owner approval: the main agent, as the owner, inspects the candidate and approves it itself with `owed_approve` (or `owed approve <node>`; delegated, no dialog; a UI confirmation only under `OWED_CONFIRM=owner`), giving a `note` and stating the approval and its reason in its report. Subagents never approve, and nobody performs the external effect before the approval is recorded. Nodes with `evidence:` items owe manual evidence: whoever the plan names (`by`: reviewer, parent or owner; never a writer of the node) actually checks it, then records `owed_evidence` (`node`, `id`, `files`, `note`, `as`) or `owed evidence <node> <id> --file <path> --note TEXT --as <role>:<id>`; the files are hashed when recorded. Never record evidence you did not check yourself; it is shown as manual, not as measured. `owed drive` halts for these only when everything else is satisfied. After a merge, record what an external effect produced (version, dist-tag, tarball) as a receipt with the same command (`files` optional, `note` required).

The `owed_why` / `owed why <node>` card lists keys and evidence for each obligation: ✔ measured or reviewed, ⚠ waived, ✘ rejected, ⊥ awaiting observation, ⊤ conflict, ⏸ deferred, ⛔ blocked. E means a pass supported by evidence, W means an owner waiver, and D means remaining debt. Also inspect "Untested changes" and ΔO⁻ (weakened or removed obligations); changes without test coverage must not be described as verified.

The status pending queues are grouped by discharger: parent+writer handle dispatch, submission, and repairs; executor handles attest; reviewer provides independent judgment; owner handles risks and downgrades. Resolve specific obligations from the queues instead of repeatedly trying merge.

Rules that must not be broken:

- Do not edit closure files to make checks pass; the executor pins the check closure from base. Necessary, genuine closure changes must explicitly receive closure-review acceptance.
- Do not self-review, disguise a writer as an independent reviewer under another name, or fabricate executor evidence.
- Initialization is an owner act: call `owed_init` (`plan`) yourself (delegated; a dialog only under `OWED_CONFIRM=owner`; never `--i-am-owner`). After `owed_init` returns, the genesis attest runs in the background; do not poll: `owed_status` shows `Genesis: k/n invariants observed`, and the session gets one `owed-init` message when it ends. `Genesis attest incomplete` means the ledger is initialized: run `owed attest --genesis` (or the next attest/merge measures the missing invariants); never re-run init. Plan edits meanwhile are fine (`owed_plan` warns that genesis is pending).
- Agents must never use `--i-am-owner`. Owner decisions (`owed_waive`, `owed_defer`, `owed_decoy` commit/reveal, `owed_adopt`, `owed_approve`, owner `owed_evidence`, downgrading `owed_plan` with `note`) are the main agent's, delegated and audited; decide them on evidence and write the reason. A subagent never makes them; under `OWED_CONFIRM=owner` without a UI, stop that decision and report it.
- The parent may update the plan through a file path with `owed_plan`; only owner may confirm downgrades, except those an `allow:` rule of the current plan covers (the parent records them; they stay in ΔO⁻, labelled `under allowance (plan #S)`). Never add or widen `allow` rules yourself (owner only), and never silently weaken acceptance conditions. When `owed why` lists out-of-writes paths, either the writer reverts them or the plan widens writes (a downgrade); a ruling cannot accept them.
- Planning: keep writes strict by default. For integration and packaging nodes, which tend to need entry files, `package.json` or wiring directories, pre-authorize those prefixes at plan time with an `allow` rule, e.g. `allow: [{nodes: ["KB*", "A9-*"], writes: ["app/src/entry/", "package.json"]}]`. A writer's writes question then costs one parent plan update and no owner step. A parent plan update refused only for widened writes ends with `hint: an allow rule {nodes: [...], writes: [...]} in the prior plan would cover this`, ready to paste into the next plan. `owed init` / `owed plan` (and the pi tools, as `warnings`) warn `warning: node <id> has no checks: its acceptance rests on review alone` for each node with no checks and no evidence obligations; nothing is refused or recorded, but give the node a check or evidence when its goal can be measured. A reviewer's ok means the candidate meets the node's goal as its title and brief state it, not only that the writer's report is accurate.
- The plan's `exec` block (`env`, `wrap`) applies to every check process owed starts (`[...wrap, "bash", "-lc", cmd]`); like `setup`, changing it is an owner act (it can weaken every check): the main agent sets it once itself as owner with a plan `note` saying why, and never lets a subagent change it. A wrapper must run the command, pass its output through and exit with its code; when it cannot run the command (transport, mirror or lease failure) it must exit 126 or 127, because any other non-zero code is read as a test failure (a red pass unless `red_expect` is set: use `red_expect` with wrappers). One that runs elsewhere (ssh) must bound the command there itself. A relative `wrap[0]` resolves against the materialized tree: use absolute paths.
- Check results: one check may chain `cargo test` and `node --test --test-reporter=tap` (the counts sum, format `mixed`). A non-red check that exits non-zero without running a recognizable test (e.g. a wrong cargo package name, exit 101) is `fail` and its note (shown in `owed why` and the repair message) carries the last 5 output lines: fix the command; exit 126/127 with no count is an `error` (the command never ran). Check processes do not inherit `DSA_*` (except `DSA_HOME`), so owed commands inside a check run as a top-level process.
- Negative observations may only be cleared by the rules. Execution failures require attribution on the original key/commit/base: another failure clears the old block; a pass creates a conflict that only an owner waiver accepting the risk of the corresponding seq clears (the main agent decides it, with a reason).
- A judgment block at rank r may only be cleared by an ok from the original reviewer at rank at least r, or another reviewer at a higher rank. Another reviewer at the same rank cannot clear it. Owner waivers must also reference `accept_risk`.
- Do not directly edit the ledger, blobs, or closure to bypass rejection. Defer only permits a specific merge to retain invariant debt; it is not a pass. Invariants cannot be waived.
