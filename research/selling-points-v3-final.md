## 1. 推荐

- **一句话：没有回执，不算完成。**
- **关键词：回执**（产品名词）＋**实测**（owner 自己的词，用来区分“真跑过”和“自称跑过”）。
- **“最顶级”只争一个维度：假完成逃逸率。** 不争速度、决定或调度。
- “放手”只在演示里出现，不作为承诺。

## 2. 北极星与次级指标

**北极星：假完成逃逸率** = 回执上的事实不成立、节点却进了 integrated 的比例。
- 诱饵：在影子集成流中按约 2% 混入封存的假完成，包括脏树、错树、零用例、`sys.exit(0)`、改规则给自己放行、越出写集、双写者、过期裁决。
- 逃逸台账：把事后的 Amendment、回滚、合入后 BLOCK 回链到当初放行它的回执，并归因为“门禁缺口”或“oracle 缺口”。
- 对手基线：同一套诱饵公开跑 GitHub required checks、Claude Code hooks、Gas Town。
- 统计限制：按三倍法则，零逃逸也需要约 270 个节点才能证明 ≤1.1%；一个 J1（约 90 个节点）最多只能证明 ≤3.3%。

**次级指标（防止刷分）**
1. owner 每日待决数 ≤15，以及每个节点花的人工分钟数。防止靠“全拒”把逃逸率压低。
2. override/误拒率 ≤10%。
3. 每次集成的父级工具调用数（沿用 DESIGN.md §12.5 的止损判据）。

## 3. 对外不能说的话

可证明正确、保证正确；独有、护城河；10 倍、世界第一（尚未实测）；更快；人只看例外、人不用看；就绪的活不空等、自动调度；“agent 会作弊，我们抓得住”；“决定一次处处生效、改了自动知道哪些失效”；开放标准；防篡改。

## 4. 推荐成立的前提（设计必须先改）

1. 删除默认采信写者自测（DESIGN.md:361-364），改为由写者触发受信 runner（SYNTHESIS.md:58）。
2. 回执加入用例数、red-first、“零用例判失败”、`rulings_seen_at_dispatch`。
3. override 和“合并后再评审”（DESIGN.md:147-148）一律显示为“无回执”。
4. 规则从可信基线加载。
5. 合并前在候选树上验证，再用 CAS 推进 ref。
6. §12.5 加入逃逸台账和诱饵。
7. 回执带上 oracle 强度：R2 及以上节点做变异测试，分数低的自动升档评审（ten-x 提出，终审列为最好的新想法之一）。

## 6. 稳定结论与仍是猜测的部分

**稳定**（多方独立得出、证据可核）：
- “决定”不做头条：75–85% 是三类耗时合计，且原文说设计返工“工具不应省掉”（DESIGN.md:411、:415）。
- 速度不是卖点：收益上限为 15–25%。
- 没有结构性护城河：机制都能复制，差异只能靠公开实测成绩证明。
- 默认采信写者自测与任何回执口号相矛盾。
- 价值在于拒收没有经过独立执行的“完成”，而不是证明代码正确。

**仍是猜测**：例外量是否可控；10 倍；各家复刻百分比；“不空等”是否普适；抢先定标准的收益；决定过期语义；暗决定雷达。

**owner 原话的核对**（终审抽核约 30 处）：owner 最强烈的不满是验收冒充，例如用“图层 ready/非空像素”代替同帧对比（xwell/tasks/2026-09-30-slice-triage-overnight.md:495）。但这类问题出在验收标准太弱，回执照样会通过，所以产品不能承诺“没有一项是冒充的完成”。“只有单 agent 在跑”那次，是 DAG 本身串行（studio-principles.md:402），不是就绪的活在空等。
