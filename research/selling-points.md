# pi-dag 卖点（v4，2026-10-08，J1 实证修订）

> 取代 v3 终版（已存为 `selling-points-v3-final.md`）。修订依据是 `j1-findings.md`：J1 合入后的 4 次真实逃逸全部来自 oracle 或覆盖缺口，触发了 v3 §5 预先设定的改口判据。
> 前几轮讨论：`selling-*.md`、`selling-r2-*.md`、`selling-r3-*.md`、`selling-final-judge.md`。

## 1. 推荐

- **一句话：没有回执，不算完成；回执写明测了什么、没测什么。**
- **关键词：回执＋验收强度。** “实测”保留为执行这一层的用词（owner 原话：“还是实测吧”，A:5316）。
- **“最顶级”只争一项：错误完成的逃逸率**，统计时把 oracle 和覆盖缺口算进去，不只看执行造假。
- “放手”只在演示里出现，不作为承诺。

**为什么改**：
- 按 v3 的说法，只证明“确实跑过”。但这一层 J1 自建的 checker 已经守住了，没有发现执行造假。
- J1 真正漏进去的是：7/7 实测但 oracle 太宽（FAULT-POWER）、回归集漏选（K4、PLAN2）、只用小 fixture（maxBuffer）。
- 所以只证明“确实跑过”的回执，只是卫生功能。差异化在于**把验收的强弱和覆盖范围摆到台面上，弱了就升档评审，候选集成时选全回归。**

## 2. 北极星与次级指标

**北极星：错误完成逃逸率**，拆成三类分别报告：
1. **执行事实逃逸**：回执上的事实（tree、clean、用例数、red/green、写集）不成立，节点却进了 integrated。
2. **oracle/覆盖逃逸**：回执事实成立，但错误在合入后才被发现，例如 Amendment、回滚或合入后 BLOCK。归因到 oracle 过宽、义务没覆盖，或者回归选择遗漏。
3. **无回执合入**：override、合并后评审、手工合入。

每类都记录实际影响：返工时长和波及的节点。

**测量手段**
- 诱饵：在影子集成流中按约 2% 混入封存的错误完成。诱饵分三组：J1 已核实事故的回放、合成威胁、第三方题目。
- 逃逸台账：把事后发现的问题回链到当初放行它的回执。
- 对手基线：同一套诱饵跑 GitHub required checks、Claude Code hooks、Gas Town。

**统计口径（修正 v3）**
- 诱饵逃逸率的分母是**诱饵次数，不是节点数**。按 2% 混入，270 个节点只有 5–6 次诱饵，不能拿来证明 ≤1.1%。
- 要在 95% 置信下用三倍法则证明 ≤1%，需要约 300 次零逃逸的诱饵试验，所以诱饵集必须单独批量跑，不能只靠影子流混入。
- 真实逃逸台账（类型 2）没有可控分母，只报告绝对次数和每 100 个集成节点的次数，不报告“率”。

**次级指标（防止刷分）**
1. owner 每天待决 ≤15。口径：去重后**首次**交给 owner 的独立事项数。等父级、等资源的不算；提醒次数和人工分钟数另外统计。
2. 误拒率、策略 override 率、证据绕过率分开定义。目标 ≤10%，超过 20% 改口，10–20% 之间观察。
3. 每次集成的父级工具调用数。
4. 验收强度检查的额外成本（变异次数 × 验收时长）。

## 3. 对外不能说的话

- 可证明正确、保证正确；
- 独有、护城河；
- 10 倍、世界第一；
- 更快；
- 人只看例外、人不用看；
- 就绪的活不空等、自动调度；
- “agent 会作弊，我们抓得住”。J1 没有发现执行作弊，这样说会夸大威胁。
- “决定一次处处生效”；
- 开放标准；
- 防篡改；
- “回放 J1 十类事故”。其中只有 4 类成立，3 类部分成立，3 类未证实。

## 4. 推荐成立的前提

1. 删除默认采信写者自测，改为由受信 runner 独立验收（PRODUCT v0.3 §4）。
2. 回执分为执行、强度、评审三个维度，并写明未测范围（PRODUCT v0.3 §3）。
3. override 和合并后评审一律显示为“无回执”。
4. 策略从可信基线读取。
5. 合并：先构造候选，再做回归选择和候选验证，最后用 CAS 推进；缺评审就拒绝合并。
6. 诱饵和逃逸台账都按上面三类分别计数。
7. R2 及以上做变异或负例检查，强度弱的自动升档评审。

## 5. 改口判据

| 出现的结果 | 改为 |
|---|---|
| 对手用现成原语跑诱饵集，与 pi-dag 差距 <2 倍 | 回执只是卫生功能，换头条 |
| 影子期每天待决 >15，或误拒/override >20% | 不再提“放手” |
| 变异/负例检查在 J1 回放上拦不住 FAULT-POWER 这类 oracle 缺口，或者成本使 P90 验收时长超过原来的 3 倍 | 撤下“验收强度”，退回“执行回执 + 合并门禁” |
| 影子期逃逸台账以执行事实逃逸为主（≥50%） | 头条回到 v3 的“实测” |
| E1 中漏注入或过期裁决 ≥4 次，或占返工 ≥15% | “裁决”回到第二层卖点 |

**已触发（2026-10-08）**：v3 的判据“oracle 缺口 ≥50% → 头条改为验收强度”。J1 回溯的结果是 4/4，但这只有 4 个样本，而且是回溯不是影子期，只算方向信号，影子期要复核。

## 6. 稳定结论与猜测

**稳定**：
- “决定”不做头条；速度不是卖点；没有结构性护城河；
- 默认采信写者自测和任何回执口号都矛盾；
- **执行真实是必要条件，不是差异化**：J1 的父级自己就做到了；
- **owner 实际的验收方式**是看行为、截图、同帧对比和逐项清单。“可验收 ≠ 已验收”是父级在清单里写的。

**仍是猜测**：
- 变异/负例检查的成本和效果（只做过 FAULT-POWER 这一例的回放推演）；
- 回归选择能否自动化，还是要项目声明；
- 待决量是否可控；
- 对手的基线。

**owner 原话的修正**：
- “不冒充”不是 owner 原话。owner 的原话是要求真实可比，例如：“studio 和 切片看着不是相同帧，我无法对比”（B:6548）；“应该显示一张和 simcluster 上完全一样的表”（同上）。“图层 ready 代替同帧对比”是父级认错时的说法（slice-triage-overnight.md:495）。
- “owner 从未提记账”收窄为：样本中没有发现 owner 主动要求做验收账本产品。owner 明确要求过记录操作经验（B:6853），以及在 tasks/ 下记录待做的工作（B:10715）。
- owner 不理解节点代号（B:8756），也问过 pi-dag 具体怎么动作（C:11708）。所以对外讲产品，要先讲一个具体例子，再讲机制。

## 7. 置信度与局限

- 方向（回执 + 验收强度）0.65；北极星的选择 0.6；12 个月内公开证明第一 0.3；“10 倍” 0.2。比 v3 略降，因为差异化现在依赖变异/负例检查的实际效果，这一点还没有实测。
- 所有数据来自 J1 一个项目；14 条事故只是样本，不是穷尽计数。
- owner 只有一人，同时是 dsa 和 pi-dag 的作者，还在调模型、买额度、推动修 dsa，不代表典型买家。
- 诱饵是自己出的题，必须封存，并引入第三方题目。
