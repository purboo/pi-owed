# Small tool surface and start

The default Pi tool profile is `core`: `owed_status`, `owed_why`, `owed_decide`, `owed_drive`, `owed_start`, `owed_submit`, and `owed_review` are direct. All other owed tools are registered at load as deferred, discoverable and activatable by the host's tool search. Core descriptions say, in both modes, that other owed operations are `owed_*` tools loadable with tool search when not declared, or reachable through the `owed <command>` CLI (`owed help`, now also a command). When a session starts, owed makes the deferred tools reachable as the host's own MCP extension does (ruling #2589, SF6): if the host reports tool exposure and has a `tool_search` that declares which tools it reaches, owed activates that `tool_search` (adding it to the active tools); if there is no such tool search, or it does not become active, owed registers its deferred tools again as direct, which declares them. Hosts that do not know exposure ignore the field and treat every tool as direct. Owed never removes a tool from the active set. `OWED_TOOLS=all` declares every owed tool directly and leaves `tool_search` untouched, so it also turns off this activation. No Pi version is assumed. A real-host smoke run was not performed: the test host has pi-coding-agent 1.0.2, older than 1.2; the behavior is covered against a fake registry modelled on pi 1.2.0.

`start` accepts optional `--plan`, `--max`, and `--stay`; `owed_start` accepts the corresponding `plan`, `max`, and `stay` fields, plus the usual optional `cwd`. It checks Git author and committer identity, validates and lints the plan, verifies the trunk ref, initializes a missing ledger as delegated `owner:pi`, records a changed plan under existing parent permissions, and starts the detached driver. Genesis measurements remain the driver's responsibility through the existing attest and merge lifecycle. Output gives the action, driver state, and next step; each lint warning is printed on its own line after the action line, and warnings remain available in structured results. When `owed_start` reuses a running driver, the session follows that driver's log from its current end, so wakes already in the log are not delivered again; a newly started driver is followed from the beginning of its fresh log.

An unchanged plan with a running driver reports `already running`, preserving the ledger and live driver log. Plan comparison uses the existing canonical plan representation, so formatting-only edits do not record a plan. When `--plan` is omitted, start rereads the latest recorded plan source rather than guessing a filename. An explicit new plan source becomes the default after a changed plan is recorded. A running driver's concurrency and stay mode are not changed by another start.

## Parent ruling

Ruling #2550 (SF4) specifies fail-closed usage refusals without a blocking dialog or ledger entry: a missing plan source must be supplied; an uncovered downgrade requires an explicit owner plan decision with a reason; and initialization under `OWED_CONFIRM=owner` requires explicit init. Allowance-covered changes use the same authority and visible downgrade accounting as plan updates. Refusals identify the failed preflight and its remedy.

`owed_dispatch` prints the complete packet once. Its rendered subagents arguments refer to that packet, while the structured subagents arguments retain the complete executable task and existing isolation setting.

## Compatibility

No ledger entry kind, acceptance gate, observation key, or plan key is changed. Genesis entries created by start may contain optional `path`, identifying the initial plan source; historical entries without it replay unchanged. A historical latest plan without a recorded source requires an explicit plan parameter. Driver-start results may contain optional `alreadyRunning`; start results expose initialization, plan update, warnings, and driver state. Existing drive start retains its refusal when another driver is running.

## Existing test changes

The existing test “G2 text/details equal the in-process views; worker errors retain exact code and text” now expects the dispatch text's packet reference instead of a second serialized packet. Its structured argument assertion is unchanged. The existing “CR2 dispatch preserves the packet and subagent arguments and appends a brief” test makes the same text-only change, retaining brief and details assertions. “SPEC §11 lists every registered pi tool” temporarily includes these notes (the decide notes fallback was removed once SPEC §11 documented decide); missing notes are tolerated after the documentation is folded. Ruling #2576 (SF5) authorizes these two assertion updates and focused rechecks in place of a second full suite. Under SF6 the existing test “registers direct typed tools and command; status uses ctx.cwd; guards become tool errors” now expects core tools direct and the other tools deferred at load (direct under `OWED_TOOLS=all`); its other assertions are unchanged.

The existing adopt-wait test “two concurrent CLI adopts share each request's 600ms total budget” is intermittent on the base tree as well, failing with the same message (the waiting adopt reports the merge lock rather than the ledger lock); this candidate does not change adopt or locking.

## Interpretation choices and limits

The only added genesis metadata is the plan source needed for omitted-plan starts. Canonical equality, existing allowance validation, driver lock serialization, and the current measurement lifecycle are reused rather than introducing new persistence or orchestration mechanisms. Initialization and plan recording remain durable if subsequent driver launch fails; explicit driver status and start recovery remain available. No unapproved deviation from SF or ruling #2550 is introduced.
